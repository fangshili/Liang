clicky 的 UI/UX 是怎么做的

对 dabit3/heyclicky-clone 的源码级拆解 —— 动效、色彩、交互节奏， 以及这些方案如何落到 Liang 的刘海光晕 / 光标光晕 / 菜单栏图标上。

Swift · SwiftUI · AppKit 20 个源文件已通读 macOS 菜单栏常驻应用 与 Liang 同赛道

01 / Overview

它到底是个什么东西

clicky 是一个常驻菜单栏、无 Dock 图标的 macOS 听写应用。按住 fn 说话 → 设备端转文字 → 粘贴到光标处； 按住 ⌥ 说话 → 截屏 + 语音指令交给 GPT-4o → 生成文本粘贴。

它和 Liang 是同一类产品：都是无窗口、常驻、用极小的视觉语言汇报一个后台进程的状态。 区别在于——clicky 的状态载体是光标旁的浮动 Pill，Liang 的是刘海边缘的光晕。 所以它的整套「如何用最小视觉表达状态机」的方法论，对 Liang 是直接可迁移的。

02 / Philosophy

五条能直接抄的设计原则

1 · 一个枚举驱动全部 UI

DictationPhase 是唯一真相源。图标、颜色、状态文案、右侧组件、菜单栏符号， 全是对这个枚举的 switch，没有任何一处「UI 自己维护的状态」。 

// PillView.swift — 四个独立的 switch，全部来自同一个 phase
private var accent: Color {
    if case .error = appState.phase { return .orange }
    return Color(red: 0.4, green: 0.8, blue: 1.0)
}

Liang 已具备 你的 LiangState + StateAppearance.appearance(using:) 是同构的，而且更完善（带 priority、isTransient）。

2 · 错误只换一个变量

整个 App 的错误态视觉，就是 accent 从蓝变橙 + 图标换成感叹号。 没有红色警告条、没有弹窗、没有震动。错误是一种颜色，不是一次事件。

对常驻工具来说，错误提示的「打扰成本」远高于「信息价值」。降级为颜色变化，是对用户注意力的尊重。

3 · 状态文案是小写、口语、带省略号

ready / listening… / thinking… / writing… / done。 全小写、无标点、进行时用 … 结尾。这不是随意——全小写降低视觉重量， 让文字退到背景里，不与波形动效争夺注意力；省略号是唯一的"进行中"信号，比 spinner 更轻。

4 · 上下文优先于自我

Pill 上显示的第一行不是 "clicky"，而是当前前台 App 的名字和图标（Gmail、Xcode…）， 只有拿不到时才回退成 "clicky"。工具在告诉你「我知道你在哪」，而不是「看，是我」。 

Text(appState.contextAppName.isEmpty ? "clicky" : appState.contextAppName)
    .font(.system(size: 11, weight: .medium))
    .foregroundStyle(.white.opacity(0.6))   // 次要信息压到 60% 不透明

5 · UI 永不拦截输入

panel.ignoresMouseEvents = true
panel.styleMask = [.borderless, .nonactivatingPanel]
panel.collectionBehavior = [.canJoinAllSpaces, .stationary, .fullScreenAuxiliary]

不吃鼠标、不抢焦点、跨所有 Space、全屏下也在。这四条是「环境感知型 UI」的准入门槛。 Liang 已具备

03 / Motion

动效拆解：三个层次

Layer 1 — 容器进出：0.14s 纯 opacity

整个 Pill 的出现和消失，只有透明度一个属性，0.14 秒。没有缩放、没有位移、没有弹簧。 

func show(mode: DictationMode) {
    position()
    panel.alphaValue = 0
    panel.orderFrontRegardless()
    NSAnimationContext.runAnimationGroup { ctx in
        ctx.duration = 0.14
        panel.animator().alphaValue = 1
    }
}

func hide() {
    NSAnimationContext.runAnimationGroup { ctx in
        ctx.duration = 0.14
        panel.animator().alphaValue = 0
    } completionHandler: { [weak self] in
        self?.panel.orderOut(nil)   // 淡出完成后才真正移出，避免闪烁
    }
}
为什么是 0.14s？ 这是「感知得到但不用等」的临界值。人眼对 <100ms 的变化几乎察觉不到过渡（显得生硬）， >200ms 开始感觉到"在等它"。100–150ms 是浮层出现的黄金区间。macOS 系统菜单的淡入正是 ~0.15s。

Layer 2 — 内容切换：SwiftUI 隐式动画

Pill 里的图标、文案、右侧组件切换没有写任何显式动画。 因为 AppState 是 ObservableObject，SwiftUI 在 @Published 变更时自动做结构过渡。 刻意不写 —— 这是「让框架干活」的典型懒惰，也是正确的。

Layer 3 — 数据驱动动效：波形

整个 App 唯一真正"有生命感"的部分，也是最值得学的部分。它只有 20 行：

struct WaveformView: View {
    let levels: [Float]
    var color: Color = .white
    var barWidth: CGFloat = 2.5
    var spacing: CGFloat = 2

    var body: some View {
        GeometryReader { geo in
            HStack(alignment: .center, spacing: spacing) {
                ForEach(Array(levels.enumerated()), id: \.offset) { _, level in
                    Capsule(style: .continuous)
                        .fill(color)
                        .frame(width: barWidth,
                               height: max(barWidth, CGFloat(level) * geo.size.height))
                }
            }
            .frame(maxWidth: .infinity, maxHeight: .infinity, alignment: .center)
            .animation(.easeOut(duration: 0.12), value: levels)  // ← 全部魔法在这一行
        }
    }
}

三个精妙细节：

  • max(barWidth, level * height) —— 静音时不塌成 0，保留 2.5pt 的圆点。波形永远"活着"，只是安静。
  • .easeOut(0.12) —— 只对最终值做平滑，不做入场动画。音频电平以 ~44Hz 更新，0.12s 的 easeOut 恰好把抖动磨平又不拖尾。
  • Capsule(.continuous) —— 不是 Rectangle。圆头让低电平时的条形看起来像"呼吸的点"而非"截断的线"。

而数据源那一侧同样克制 —— RMS 之后只做一次线性放大：

// DictationEngine.swift
let rms = sqrt(sum / Float(count))
let scaled = min(1, max(0, (rms * 12)))   // ponytail 式：一个魔法数字搞定，没有 EQ、没有 FFT
return scaled

04 / Color

色彩体系：两个颜色，五个透明度

clicky 的整套配色只有两个有彩色，其余全部是白色的不同透明度叠在纯黑上。 这是极简 macOS 浮层的标准做法。

角色取值为什么
底板.black.opacity(0.92)不是纯黑 —— 8% 透光让浮层与桌面产生轻微联系，避免"贴纸感"
描边.white.opacity(0.08)在深色底上勾出边界，比阴影更省，且在任何壁纸上都成立
阴影black 35% / r=20 / y=8y 偏移只有 8 而 radius 有 20 —— 弥散大于位移，是"悬浮"不是"抬起"
强调色底accent.opacity(0.18)同一个 accent 变量做 18% 当容器背景，色相天然一致，不需要额外定义
次要文字white 60%60% 是深色底上"可读但不抢眼"的甜点值
核心洞察： 用 accent.opacity(x) 派生整套相关颜色，而不是硬编码多个色值。 换 accent 时整个组件自动协调 —— 这正好是 Liang「状态颜色可自定义」功能需要的模式。

06 / Comparison

Liang 现状对照

读完 clicky 之后回看 Liang 的代码，结论比预期好：架构层面 Liang 已经更强了，差距集中在动效的物理感与色彩的层级化。

维度clickyLiang 现状判定
状态机 6 case，无优先级 7 case + priority + isTransient + 去重窗口 + 超时恢复 Liang 更强
状态→外观映射 散在 View 里的 4 个 switch 集中在 StateAppearance.appearance(using:)，返回 Optional 支持逐状态禁用 Liang 更强
配色 2 色 + 白色透明度阶梯，高度克制 7 个饱和纯色（#00FF52、#00BFFF…），互相竞争 需调整
动效曲线 easeOut + linear，2 条 全部 easeInEaseOut + autoreverses 需分化
状态切换过渡 SwiftUI 隐式动画自动接管 removeAllAnimations() → 立即换色，硬切 明显缺口
数据驱动动效 波形随音频电平实时起伏 无 —— 光晕节奏与实际工作量无关 可新增
上下文感知 显示前台 App 名 + 图标 已有 CursorLabelWindow，可扩展 可新增
窗口行为 borderless / nonactivating / allSpaces 同等配置 + 睡眠唤醒处理 + 多屏定位 Liang 更强

最关键的三个缺口

① 状态切换是硬切，没有过渡
GlowView.apply() 里先 removeAllAnimations() 再直接赋新 strokeColor。 从 processing(青) 跳到 success(绿) 是瞬间跳变。clicky 的 SwiftUI 隐式动画天然规避了这点， 但你在 CALayer 层必须显式加。这是感知上"廉价 vs 精致"的最大分水岭。
② 七个纯色饱和度过高且缺少统一逻辑
#00FF52 是纯绿、#00BFFF 是纯青。在刘海边缘做发光描边时， 高饱和纯色会有色带（banding）和边缘溢色。clicky 用 rgb(0.4, 0.8, 1.0) —— 三个通道都不到顶， 这是发光元素避免过曝的常规做法。
③ 所有动画都是同一条 easeInEaseOut + autoreverses
breathing / slowPulse / fastPulse / urgentPulse 只有 duration 不同（3.0/1.8/0.9/0.4）。 这让"急促闪烁"只是"快速呼吸"，缺乏性质上的差异。真正的 urgent 应该改变曲线形状，不只是速度。

07 / Proposal

Liang 的改造方案

P0 · 状态间颜色过渡（最高性价比）

一次改动，感知提升最大。在 GlowView.apply() 的 removeAllAnimations() 之前， 先跑一段 0.35s 的颜色补间。 

// GlowView.swift — 在 apply(settings:color:animationMode:) 开头插入
private var lastColor: NSColor?

func apply(settings: GlowSettings, color: NSColor, animationMode: StateAppearance.AnimationMode) {
    let alpha = CGFloat(settings.brightness)
    let baseColor = color.withAlphaComponent(1.0)

    // ponytail: 只在颜色真的变了时才补间，同色重复 apply 不动画
    let needsTransition = lastColor != nil && lastColor != baseColor
    lastColor = baseColor

    // ...原有 path / strokeColor / shadow 设置保持不变...

    glowLayer.removeAllAnimations()
    accentLayer.removeAllAnimations()

    if needsTransition {
        let fade = CATransition()
        fade.duration = 0.35
        fade.timingFunction = CAMediaTimingFunction(name: .easeInEaseOut)
        glowLayer.add(fade, forKey: "stateChange")
        accentLayer.add(fade, forKey: "stateChange")
    }

    // ...原有 switch animationMode...
}
为什么 0.35s？ 状态变化是"信息事件"，不是"操作反馈"。操作反馈要 <0.15s（即时感）， 信息事件要 0.3–0.4s（能被注意到，但不打断）。太快用户会漏掉状态变了，太慢会觉得系统迟钝。

P1 · 降低饱和度，向 clicky 配方靠拢

把纯色改成"三通道都不到顶"的发光友好色。同一色相，观感更高级，且消除 Retina 上的边缘溢色。

P2 · 让四种动画在「曲线形状」上真正不同

现在四种模式共用 easeInEaseOut + autoreverses，只有 duration 不同。 应该让每种模式有自己的性格：

模式现在建议曲线性格
breathingeaseInEaseOut 3.0s保持不变平静、有机、像呼吸
slowPulseeaseInEaseOut 1.8seaseOut 单向 + 长暗期"叩门"感 —— 亮起后缓慢暗下，等待你回应
fastPulseeaseInEaseOut 0.9seaseOut 快亮慢灭，不循环，播 2 次庆祝感 —— 成功是一次性事件，不该永远闪
urgentPulseeaseInEaseOut 0.4scubic(0.9, 0, 0.1, 1) 近方波警报感 —— 硬边切换，与呼吸有质的区别
// StateAppearance.swift — 让模式自带曲线，而不是只带时长
extension StateAppearance.AnimationMode {
    var timing: CAMediaTimingFunction {
        switch self {
        case .steady, .breathing:
            return CAMediaTimingFunction(name: .easeInEaseOut)
        case .slowPulse, .fastPulse:
            return CAMediaTimingFunction(name: .easeOut)
        case .urgentPulse:
            // 近方波：亮灭之间几乎没有过渡，与"呼吸"形成性质区别
            return CAMediaTimingFunction(controlPoints: 0.9, 0, 0.1, 1)
        }
    }

    var repeats: Float {
        // success 是一次性事件：闪 2 次就停，不无限循环
        self == .fastPulse ? 2 : .greatestFiniteMagnitude
    }
}

P3 · 数据驱动的光晕强度（对标波形）

clicky 最有生命力的是波形随音量起伏。Liang 的等价物：让 processing 的呼吸速度随 Hook 事件频率变化。

你的 CursorHookAdapter 已经在接收 preToolUse、beforeShellExecution 等事件。 统计最近 10 秒的事件数，映射到呼吸周期：密集调用工具 = 快速呼吸（AI 在忙），长时间无事件 = 缓慢呼吸（AI 在思考）。 

// StateEngine.swift — 新增，约 12 行
private var recentEventTimes: [Date] = []

/// 最近 10s 的事件密度 → 0...1。用于调制 processing 的呼吸速度。
var activityLevel: Double {
    let cutoff = Date().addingTimeInterval(-10)
    let n = recentEventTimes.filter { $0 > cutoff }.count
    // ponytail: 线性映射，8 个事件封顶。够用了，要更准再换指数衰减。
    return min(1.0, Double(n) / 8.0)
}

// 在 handle(event:) 里追加：
recentEventTimes.append(Date())
if recentEventTimes.count > 32 { recentEventTimes.removeFirst(recentEventTimes.count - 32) }

然后在 GlowView 里：duration = 3.0 - activityLevel * 1.8（空闲 3.0s ↔ 繁忙 1.2s）。 新增 这会让 Liang 从"状态灯"变成"活体指示器" —— 这是 clicky 波形给人的核心感受。

P4 · 上下文感知（低优先级）

clicky 显示前台 App 名。Liang 的等价：CursorLabelWindow 展示当前活跃的 IDE 名或正在执行的工具名 （Read、Bash、Edit）。Hook 事件里已有这些元数据。 建议缓做 —— 先做 P0–P2，视觉收益远高于此。

Liang · 状态到视觉

// 单一入口，返回 Optional 支持禁用
func appearance(using s: GlowSettings)
      -> StateAppearance? {
  guard s.isStateGlowEnabled(self) else {
    return nil
  }
  let color = s.stateColors[self]
    ?? StateAppearance.defaultColors[self]
    ?? NSColor(hex: "#808080")

  switch self {
  case .idle:       return .init(color, .breathing)
  case .processing: return .init(color, .breathing)
  case .waiting:    return .init(color, .slowPulse)
  case .success:    return .init(color, .fastPulse)
  case .error:      return .init(color, .urgentPulse)
  default:         return .init(color, .steady)
  }
}

架构更优 —— 集中、可配置、可禁用。保持这个设计。

唯一需要小心的：idle 和 processing 都是 breathing

.idle 和 .processing 都返回 .breathing，仅靠颜色区分。 如果用户改了颜色（你支持自定义），两个状态可能视觉上无法区分。 建议： idle 用 duration 4.0 的极慢呼吸 + 更低的 minIntensity(0.25)， processing 用 2.0–3.0 可变速呼吸。让节奏本身携带信息，不完全依赖颜色。

09 / Roadmap

落地顺序

P0 · 状态切换颜色补间 ~15 行
GlowView + CursorGlowView 各加一个 CATransition(0.35s)。 感知提升最大，改动最小。先做这个。
P1 · 默认配色降饱和 ~5 行
改 StateAppearance.defaultColors 五个 hex 值。 注意：老用户已持久化了旧颜色，只影响新用户和「恢复默认」。
P2 · 动画曲线差异化 ~25 行
给 AnimationMode 加 timing 和 repeats 计算属性， addBreathingAnimation 改用它们。顺带解决 success 无限闪的问题。
P3 · 事件密度驱动呼吸速度 ~20 行
StateEngine.activityLevel → 调制 processing 的 duration。 这是 clicky 波形在 Liang 语境下的等价物，产品差异化价值最高。
P4 · idle/processing 节奏区分
idle 降到 4.0s + minIntensity 0.25，摆脱对颜色的依赖。
P5 · 上下文标签 缓做
CursorLabelWindow 显示当前工具名。等前面都做完再评估。

一句话总结

clicky 的秘密不是复杂的动效，而是极度的克制 —— 两个颜色、两条缓动、0.14 秒。 Liang 的架构已经比它更完善，需要补的是三件事： 状态之间要有过渡、颜色不要顶到饱和、不同状态的动画要有不同性格。 加起来不到 70 行代码。
